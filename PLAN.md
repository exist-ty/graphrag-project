# GraphRAG on LightRAG + Google AI Studio (Gemini)

## Context

A pet-project GraphRAG system is needed, built on LightRAG (entities, relationships,
edge cases), with LLM-powered document processing into a graph and a separate embedding
model — both accessed via a single Google AI Studio API key. Since there are no real
documents yet, the knowledge base is populated with synthetic data generated by the same
LLM, specifically designed to exercise complex GraphRAG scenarios (aliases, homonyms,
contradictions, temporal fact changes, nested hierarchies, multi-hop relationships,
sparse nodes).

Everything runs **locally, without a server**: LightRAG stores the graph and vectors
in files by default (NetworkX + nano-vectordb) in the process working directory; the
only outbound traffic is HTTPS calls to the Gemini API. The only "server" is the
optional `lightrag-server`, which is also just a local process with a web UI on
`localhost`.

The synthetic data theme was chosen through a consensus poll of three independent models
(Gemini/Groq/Nemotron via `mcp__llm__consult`) and synthesized into:

**Aurelia Sector** — a cyber-feudal interstellar empire (houses, megacorporations,
colonies, fleets). The key generation methodology (taken from the Nemotron response):
first, a **single "ground truth" timeline and entity registry** is established, then
documents are generated from **different biased narrators** referencing this timeline —
this is the only way to produce genuine, controlled contradictions in the text rather
than random noise.

Models (verified directly via API by calling `GET /v1beta/models` with the user's
key — both IDs confirmed as available on the account):
- LLM for entity/relationship extraction: **`gemini-3.6-flash`**
- Embedding model: **`gemini-embedding-2`** (stable, multimodal,
  input limit 8192 tokens — better than `gemini-embedding-001`)

The API key is stored only in `.env` (not in code, not in chat, not in the plan) —
standard pattern for secrets.

## Recommended Approach

### Project Structure
```
graphrag-project/
  .env                          # GEMINI_API_KEY (already created)
  .venv/                        # (already created)
  data/generated/                # synthetic .md documents
  rag_storage/                   # LightRAG working_dir (graph+vectors, file storage)
  scripts/
    generate_synthetic_data.py
    build_kg.py
    query_example.py
```

### 1. Synthetic Data Generator — `scripts/generate_synthetic_data.py`
Uses the `google-genai` SDK directly with `gemini-3.6-flash` (not via llm-mcp — which
has hardcoded models, as noted by the user). Two passes:
1. **Seed pass**: a single LLM call generates the "ground truth" — event timeline,
   entity registry (houses, corporations, persons with real names and aliases,
   stations/ships with homonymous names, ownership/subordination hierarchy) in a
   structured format (JSON), saved to `data/ground_truth.json`.
2. **Divergent pass**: for each timeline entry/entity, documents are generated from
   different "narrators" (official encyclopedia, spy dossier, propaganda/news,
   ship/station logs, decrees and rumors) — with deliberately diverging versions of
   facts, different naming of the same entities, varying levels of detail. ~1000
   documents following the consensus proposals (300 encyclopedia / 250 dossier /
   250 news-propaganda / 200 logs; volume can be reduced for a smoke test). Saved as
   individual `.md` files in `data/generated/`.

### 2. Ingestion Pipeline — `scripts/build_kg.py`
LightRAG already includes built-in Gemini bindings in `lightrag.llm.gemini`
(confirmed by reading the package source code):
- `gemini_complete_if_cache(...)` — LLM function for entity/relationship extraction,
  model `gemini-3.6-flash`, key taken from `.env`.
- `gemini_embed(...)`, wrapped with the `@wrap_embedding_func_with_attrs` decorator —
  embedding function. **Before final integration, the actual vector dimensionality of
  `gemini-embedding-2` must be empirically verified** with a single test call to
  `embedContent` (for `-001` it differs from the documented value; for `-2` the
  dimensionality is not published in the API listing) — and only then should
  `embedding_dim` be set in `EmbeddingFunc`, otherwise the entire storage will need
  to be re-embedded if there's an error.

`LightRAG(working_dir="rag_storage", llm_model_func=..., embedding_func=...)`,
then `await rag.initialize_storages()` and `await rag.ainsert(...)` for all files
from `data/generated/`.

### 3. Query Interface — `scripts/query_example.py`
A minimal CLI on top of `rag.aquery(question, param=QueryParam(mode=...))` —
sufficient for a smoke test of the pipeline. The choice of primary interface (built-in
`lightrag-server` with Web UI / MCP wrapper over `LightRAG.query()` for access from
Claude Code / plain CLI) was deferred by the user — none of this is being built until
explicitly requested.
