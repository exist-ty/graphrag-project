# GraphRAG на LightRAG + Google AI Studio (Gemini)

## Context

Нужна pet-проектная GraphRAG-система на базе LightRAG (сущности, связи, edge cases),
с LLM-обработкой документов в граф и отдельной embedding-моделью — обе через один
Google AI Studio API-ключ. Так как реальных документов пока нет, база наполняется
синтетическими данными, сгенерированными той же LLM, специально спроектированными
так, чтобы упражнять сложные случаи graphRAG (алиасы, омонимы, противоречия,
временные изменения фактов, вложенные иерархии, multi-hop связи, разреженные узлы).

Всё разворачивается **локально, без сервера**: LightRAG по умолчанию хранит граф и
векторы в файлах (NetworkX + nano-vectordb) в рабочей директории процесса; наружу
идут только HTTPS-вызовы к Gemini API. Единственный «сервер» — опциональный
`lightrag-server`, который тоже просто локальный процесс с веб-UI на `localhost`.

Тема синтетических данных выбрана через consensus-опрос трёх независимых моделей
(Gemini/Groq/Nemotron via `mcp__llm__consult`) и синтезирована в:

**Aurelia Sector** — кибер-феодальная межзвёздная империя (дома, мегакорпорации,
колонии, флоты). Ключевая методика генерации (взята от Nemotron-ответа): сначала
фиксируется **единый "ground truth" таймлайн и реестр сущностей**, затем документы
генерируются от **разных предвзятых нарраторов**, ссылающихся на этот таймлайн —
только так в тексте появляются настоящие, контролируемые противоречия, а не
случайный шум.

Модели (проверено напрямую через API вызовом `GET /v1beta/models` с ключом
пользователя — оба id подтверждены доступными на аккаунте):
- LLM для извлечения сущностей/связей: **`gemini-3.6-flash`**
- Embedding-модель: **`gemini-embedding-2`** (стабильная, мультимодальная,
  input limit 8192 токенов — лучше чем `gemini-embedding-001`)

Ключ API хранится только в `.env` (не в коде, не в чате, не в плане) — стандартный
паттерн для секретов.

## Рекомендуемый подход

### Структура проекта
```
graphrag-project/
  .env                          # GEMINI_API_KEY (уже создан)
  .venv/                        # (уже создан)
  data/generated/                # синтетические .md документы
  rag_storage/                   # LightRAG working_dir (граф+векторы, файловое хранилище)
  scripts/
    generate_synthetic_data.py
    build_kg.py
    query_example.py
```

### 1. Генератор синтетических данных — `scripts/generate_synthetic_data.py`
Использует `google-genai` SDK напрямую с `gemini-3.6-flash` (не через llm-mcp — там
хардкод моделей, о котором писал пользователь). Два прохода:
1. **Seed-проход**: один вызов LLM генерирует "ground truth" — таймлайн событий,
   реестр сущностей (дома, корпорации, персоны с настоящими именами и алиасами,
   станции/корабли с омонимичными названиями, иерархию владения/подчинения) в
   структурированном виде (JSON), сохраняется в `data/ground_truth.json`.
2. **Divergent-проход**: по каждому пункту таймлайна/сущности генерируются
   документы от разных "нарраторов" (официальная энциклопедия, шпионское досье,
   пропаганда/новости, судовые/станционные журналы, указы и слухи) — с намеренно
   расходящимися версиями фактов, разным именованием одних и тех же сущностей,
   разной степенью детализации. ~1000 документов по образцу consensus-предложений
   (300 энциклопедия / 250 досье / 250 новости-пропаганда / 200 журналы, объём
   можно урезать для смоук-теста). Сохраняются как отдельные `.md` файлы в
   `data/generated/`.

### 2. Пайплайн ингестии — `scripts/build_kg.py`
LightRAG уже содержит готовые Gemini-байндинги в `lightrag.llm.gemini`
(подтверждено чтением исходников пакета):
- `gemini_complete_if_cache(...)` — LLM-функция для извлечения сущностей/связей,
  модель `gemini-3.6-flash`, ключ берётся из `.env`.
- `gemini_embed(...)`, обёрнутая декоратором `@wrap_embedding_func_with_attrs` —
  embedding-функция. **Перед финальной обвязкой обязательно эмпирически проверить
  реальную размерность вектора** `gemini-embedding-2` одним тестовым вызовом
  `embedContent` (у `-001` она отличается от заявленной, у `-2` в апи-листинге
  размерность не публикуется) — и только потом фиксировать `embedding_dim` в
  `EmbeddingFunc`, иначе придётся переэмбеддить всё хранилище при ошибке.

`LightRAG(working_dir="rag_storage", llm_model_func=..., embedding_func=...)`,
далее `await rag.initialize_storages()` и `await rag.ainsert(...)` по всем файлам
из `data/generated/`.

### 3. Интерфейс запросов — `scripts/query_example.py`
Минимальный CLI поверх `rag.aquery(question, param=QueryParam(mode=...))` —
достаточно для смоук-теста конвейера. Выбор основного интерфейса (встроенный
`lightrag-server` с Web UI / MCP-обёртка поверх `LightRAG.query()` для обращения
из Claude Code / просто CLI) пользователь отложил на потом — ничего из этого не
делаем, пока не попросит явно.

## Верификация
1. Сгенерировать маленькую партию (~20-30 документов) вместо полной 1000 —
   проверить, что seed+divergent генерация реально производит противоречия,
   алиасы и т.д. (глазами, по паре примеров).
2. Прогнать `build_kg.py` на этой партии, убедиться что `rag_storage/` заполнился
   (граф, vector db, kv store — файлы появились и не пустые).
3. Сделать 2-3 тестовых запроса через `query_example.py` в разных режимах
   (local/global/hybrid) и вручную сверить, что ответы отражают факты и
   противоречия из `ground_truth.json`.
4. Только после этого — предложить пользователю масштабировать генерацию до
   полного объёма (расход API-квоты пропорционален объёму, поэтому не делать
   это до валидации на малой партии).
